# Plan Todo Tool Plan

## Summary

Implement a visible session task plan for Topchester through a new agent-facing `plan_todo` tool.

The target outcome is that long-running or multi-step coding work shows a compact, trustworthy plan in the TUI while the agent works. The model should update the plan as work progresses, with exactly one active item at a time. The state is session task state only. It is not KB data, not persisted project knowledge, and not a substitute for implementation plans under `docs/plans/`.

This plan expands the `### 5. plan_todo` item from `docs/plans/2026-05-13-alpha-tool-gap-analysis-plan.md` and assumes the tool protocol work in `docs/plans/2026-05-13-auto-tool-protocol-plan.md` is already available. In particular, `plan_todo` should be a normal registered `ToolDefinition` so native OpenAI-compatible tools, text JSON fallback, and XML fallback all see the same schema.

## Decisions

- Add one new model-visible tool named `plan_todo`.
- Use the existing tool registry, parser, executor, native schema adapter, and runtime loop.
- Keep the V0 contract as a full replacement of the current plan, not incremental operations.
- Use task statuses `pending`, `in_progress`, and `completed`.
- Require at most one `in_progress` item.
- Allow zero `in_progress` items only when every item is `completed` or when clearing the plan.
- Keep plan state scoped to one runtime/session. Do not write it into the KB/session overlay.
- Show the current plan in the TUI as pinned UI state, not as repeated assistant prose.
- Persist plan update events in the session log so resumed sessions can restore the visible plan.
- Keep `plan_todo` non-mutating with respect to the workspace.
- Do not add user-editable todo commands in the first pass.

## Scope

Included:

- `plan_todo` tool schema, result type, prompt text, registry entry, parser/native conversion coverage, and executor logging metadata.
- Runtime-owned task plan state for each `TopchesterAgentRuntime` instance.
- A new runtime event that carries the current task plan to the TUI and session persistence.
- TUI rendering for the current plan during multi-step work.
- Resume/static rendering support for persisted task plan events.
- Prompt guidance that asks the model to create and maintain a plan for non-trivial tasks.
- Tests for tool schema validation, one-active-item enforcement, runtime event flow, session persistence, resume context filtering, TUI rendering, and smoke behavior.
- Docs updates for interactive behavior and the alpha checklist.

Not included:

- KB storage or KB graph integration for task plans.
- Project-level planning documents generated by the tool.
- User commands for editing the plan manually.
- Cross-session semantic merging of old plans.
- Subagents or parallel task scheduling.
- Real-time streaming partial-plan updates while a model response is still in flight.
- Enforcing model honesty beyond schema checks and visible state.

## Current State

Topchester already tells the model:

- `src/agent/prompts.ts` says to break multi-step work into an internal plan and use a planning/todo tool if one exists.
- No planning tool currently exists in `src/agent/tools/registry.ts`.
- No runtime event currently represents task-plan state in `src/agent/events.ts`.
- `src/tui/layout.ts` already owns visible UI state for status, KB status, ephemeral lines, notice lines, prompt hints, and modal state.
- `src/tui/shell.ts` already maps runtime events to TUI state and persisted session payloads.
- `src/session/events.ts` persists message, tool call, status, knowledge status, and choice payloads.
- `src/agent/runtime.ts` already runs a bounded single-tool loop and formats each tool result back into the next model prompt.
- `src/model/index.ts` already normalizes native tool calls and text fallback tool calls through `ToolDefinition.argsSchema`.

Important baseline:

- Normal coding work must continue to go through the project knowledge path; `plan_todo` only makes the task plan visible.
- Tool rows are filtered from model context on resumed sessions. Persisted task-plan events should also stay out of future model context unless deliberately summarized into a user-visible assistant message later.
- The tool loop currently executes one tool call per model step. `plan_todo` therefore naturally consumes a step before another tool can run.

## Recommended Contract

Suggested V0 tool call:

```json
{
  "tool": "plan_todo",
  "args": {
    "items": [
      {
        "text": "Inspect runtime and TUI event flow",
        "status": "completed"
      },
      {
        "text": "Add task-plan runtime event and state",
        "status": "in_progress"
      },
      {
        "text": "Add TUI rendering and persistence tests",
        "status": "pending"
      }
    ]
  }
}
```

Suggested args:

```ts
type PlanTodoStatus = "pending" | "in_progress" | "completed";

interface PlanTodoItemInput {
  text: string;
  status: PlanTodoStatus;
}

interface PlanTodoToolArgs {
  items: PlanTodoItemInput[];
}
```

Suggested internal state:

```ts
interface TaskPlanItem {
  text: string;
  status: PlanTodoStatus;
}

interface TaskPlanState {
  items: TaskPlanItem[];
  updatedAt: string;
}
```

Suggested result:

```ts
interface PlanTodoToolResult extends ToolResult<"plan_todo"> {
  plan: TaskPlanState;
  pendingCount: number;
  inProgressCount: number;
  completedCount: number;
}
```

Suggested tool result text:

```text
Plan updated
pending: 1
in_progress: 1
completed: 1
current: Add task-plan runtime event and state
```

Prompt guidance should tell the model:

- Use `plan_todo` for non-trivial, multi-step work before the first substantive tool call.
- Keep the list short, usually 2 to 6 items.
- Maintain exactly one `in_progress` item while work remains.
- Update the plan after completing a major step or when new evidence changes the work.
- Do not use `plan_todo` for one-step answers, simple reads, or tiny edits.
- Do not include hidden chain-of-thought, speculation, or private reasoning in plan item text.
- Clear the plan with `items: []` only when abandoning a plan or after the final response does not need a visible active plan.

## Implementation Shape

Add a small session task-plan module, probably `src/agent/task-plan.ts`, that owns:

- `PlanTodoStatus`
- `TaskPlanItem`
- `TaskPlanState`
- `planTodoArgsSchema`
- `createEmptyTaskPlanState()`
- `applyTaskPlanUpdate(previous, args, now)`
- `summarizeTaskPlan(state)`
- `formatTaskPlanForPrompt(state)`
- `formatTaskPlanForTui(state, width)`

The `plan_todo` tool should live in `src/agent/tools/plan-todo.ts` and delegate all state mutation through a runtime-provided task-plan controller. Because `ToolContext` currently only has workspace/logging fields, add an optional `taskPlan` capability to the tool context:

```ts
interface ToolContext {
  workspaceRoot: string;
  pathEnv?: string;
  logger?: Logger;
  taskPlan?: TaskPlanController;
}

interface TaskPlanController {
  update(args: PlanTodoToolArgs): TaskPlanState;
  get(): TaskPlanState;
}
```

Then extend `ExecuteToolCallOptions` to accept `taskPlan?: TaskPlanController` and pass it into `ToolContext`. This keeps `plan_todo` as a normal registered tool without adding global mutable state.

Runtime flow:

1. `TopchesterAgentRuntime` creates a task-plan controller per runtime instance.
2. Runtime passes that controller to `executeToolCall(...)`.
3. `plan_todo` validates and replaces the current plan.
4. The tool result returns compact counts and the current active item.
5. Runtime emits both the normal `tool_call` row and a new `task_plan` event after successful `plan_todo` execution.
6. TUI shell applies the `task_plan` event to the layout.
7. Session persistence records the `task_plan` event for resume.
8. The next model prompt receives the normal tool result plus continuation guidance.

Do not special-case `plan_todo` in the model gateway. The auto tool protocol work should handle it through the registry.

## Data Flow

```text
model -> plan_todo tool call
      -> parse/native schema validation
      -> executeToolCall(..., taskPlan)
      -> taskPlan.update(args)
      -> PlanTodoToolResult
      -> AgentToolCallEvent + AgentTaskPlanEvent
      -> TUI pinned plan + session task_plan payload
      -> next model prompt includes compact tool result
```

For non-plan tools, the runtime should not mutate task-plan state automatically. The model remains responsible for calling `plan_todo` when progress changes. A later slice can add warnings if a long tool sequence never updates the plan.

## TUI Shape

V0 should render the current plan as a compact pinned block above the prompt, below slash suggestions if they are visible. It should not be a floating card, modal, or repeated chat message.

Suggested visual shape:

```text
plan
  [x] Inspect runtime and TUI event flow
  [>] Add task-plan runtime event and state
  [ ] Add TUI rendering and persistence tests
```

Rendering rules:

- Hide the block when there are no plan items.
- Use ASCII fallback markers if needed in tests, but match existing TUI style if the current UI already uses symbols.
- Truncate long item text to the available width.
- Cap visible items at a small number, such as 6, and show `+N more` if needed.
- Do not reduce the prompt below a usable one-line input.
- In static non-interactive output, render the last restored task plan before the prompt if the session has one.

## Session And Resume Shape

Add a new persisted payload kind:

```ts
interface TaskPlanPayload {
  kind: "task_plan";
  items: TaskPlanItem[];
  updatedAt: string;
}
```

Session behavior:

- Persist each successful plan update.
- On resume, replay the latest `task_plan` payload into the TUI state.
- Do not add task-plan payloads to `ChatLayout.getConversationTurns()`.
- Keep old session logs readable by adding the new schema union member without changing existing payload versions unless the session format policy requires a version bump.
- Static rendering should include current plan state only once, not every historical update.

If resume hydration currently happens outside the layout, add the smallest adapter that converts resumed `task_plan` payloads into layout state instead of chat messages.

## Cross-Slice Rules

- Keep `plan_todo` session-only and separate from the KB.
- Keep plan text short and user-safe; no hidden reasoning or file contents in task item text.
- Preserve the existing native/text tool protocol behavior.
- Require at most one active item everywhere: schema, helper tests, and runtime state.
- Do not make the TUI plan block part of model conversation context.
- Do not let `plan_todo` count as workspace mutation or KB dirty state.
- Keep the UI compact enough that the prompt remains usable on narrow terminals.
- Keep fake API smoke deterministic and avoid requiring live providers for acceptance.
- Treat smoke tests as runtime/CLI end-to-end coverage, not as the primary test for terminal rendering.
- Treat TUI render tests as the primary coverage for the pinned plan block.
- Use live API smoke only as optional confidence that real models adopt `plan_todo` under the normal prompt and tool schema.

## Testing Plan

Unit tests:

- Task-plan validation accepts valid short plans.
- Validation rejects empty item text, duplicate item text, multiple active items, and no-active unfinished plans.
- `plan_todo` appears in the registry and prompt lines.
- Native AI SDK tool conversion includes `plan_todo`.
- JSON and XML text parsing keep using the shared schema validation.
- Executor logging summarizes plan metadata without dumping unnecessary internals.

Runtime tests:

- `plan_todo` updates runtime-owned state.
- Runtime emits `tool_call` and `task_plan` events after successful updates.
- Invalid plan updates do not change current state.
- Plan tool result appears in the next model prompt.
- The tool loop can still complete a multi-step task with plan updates.

TUI/session tests:

- Pinned plan renders only when there are items.
- Exactly one in-progress item is visually distinct.
- Long item text truncates.
- Small terminals keep the prompt visible.
- `task_plan` persists and resumes as UI state.
- Persisted task-plan events do not become model conversation turns.

Smoke tests:

- Fake API scenario uses `plan_todo` before substantive work.
- Fake API smoke verifies runtime events, session persistence, report fields, and final task completion.
- Smoke reports include enough plan metadata to diagnose missing updates.
- Full fake API battery remains green.
- Live API smoke is optional and checks model adoption, not deterministic correctness.
- Full interactive TUI smoke would require a PTY harness and is out of scope for V0.

## Open Questions

- Should a completed final plan remain visible after the final answer, or should runtime clear it automatically after all items are completed?
- Should task-plan events require a session event version bump, or is adding a discriminated union member enough for current compatibility expectations?
- Should `plan_todo` allow an optional short `explanation` field, or keep V0 item-only to avoid encouraging hidden reasoning?
- Should the TUI use Unicode symbols for markers, or ASCII markers for maximum terminal compatibility?
- Should `topchester run --json` expose task-plan events by default? The likely answer is yes because it already emits structured runtime events.

## Implementation Notes

- Prefer full-replacement plan updates for V0. Incremental `add/update/remove` operations can come later if model behavior proves too verbose.
- Keep the plan state controller owned by runtime, not `AppContext`, unless future slash commands need to inspect or modify it.
- If `plan_todo` frequently consumes too much of the 8-call loop on real tasks, revisit the tool-call limit with smoke data instead of raising it preemptively.
- The current prompt already references planning tools generically, so adding the tool may immediately affect model behavior once native schemas are available.
